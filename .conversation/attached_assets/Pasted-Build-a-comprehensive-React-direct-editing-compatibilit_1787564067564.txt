Build a comprehensive React direct-editing compatibility lab named “React Visual Editor Torture Test.”

Purpose:
This application will be used to test Replit’s Element Selector and Visual Editor across HTML elements, React rendering patterns, Tailwind styles, custom components, repeated components, dynamic content, and difficult DOM-to-source mappings.

The application must make it easy to test one element at a time and record whether:

1. The element can be selected.
2. The correct source element is identified.
3. Inline text editing is available.
4. Style controls are available.
5. The preview updates immediately.
6. Save updates the correct source code.
7. Discard restores the original state.
8. Editing one instance unexpectedly changes other instances.
9. React functionality still works after saving.
10. The app still builds without console or TypeScript errors.

Technology constraints:

- React 19
- TypeScript
- Vite
- Tailwind CSS
- No external UI component library
- Build all components locally
- Use semantic HTML wherever possible
- Do not manually add or modify `data-replit-metadata`, `data-component-name`, or other Replit-owned instrumentation
- Add human-readable `data-testid` values to test targets
- Keep the application entirely client-side
- Do not add a database or backend
- Do not use dangerous remote scripts
- Use only safe local assets, data URLs, or stable public sample media
- The final app must run successfully without TypeScript, build, or browser-console errors

Important:
Do not “simplify” or consolidate the test cases. Many sections intentionally render visually similar elements using different React source patterns. Their differences are the point of the lab.

APPLICATION STRUCTURE

Create a polished documentation-style application with:

- A sticky left navigation listing every test category.
- A sticky top bar containing:
  - App title
  - Search/filter field
  - “Show all”
  - “Only expected direct edits”
  - “Only expected Agent fallback”

- A responsive mobile layout.

- Clear focus states and accessible labels.

Every test case must be displayed in a bordered card containing:

- Unique test ID, such as TEXT-001.
- Test-case title.

  - Direct edit
  - Changes all instances
  - Agent fallback expected
  - Selection only

- A short “Manual test” instruction.
- An “Interaction result” area when applicable.

Give the test target itself a data-testid matching the test ID, for example:

data-testid="TEXT-001-target"

Do not put the test ID only on the outer card. Put it on the element users should select.

REACT SOURCE-PATTERN TESTS

Create visually similar elements implemented with each of the following patterns. Keep each as a separate test case.

A. Text ownership patterns

- Plain literal:
  <p>Literal text</p>

- String expression:
  <p>{"String expression"}</p>

- Variable binding:
  <p>{title}</p>

- Object-property binding:
  <p>{product.name}</p>

- Mixed literal and expression:
  <p>Hello {userName}!</p>

- Mixed direct and nested text:
  <p>Hello <strong>important</strong> world</p>

- Multiple direct text segments:
  <p>Before <span>middle</span> after</p>

- Conditional text:
  <p>{enabled ? "Enabled" : "Disabled"}</p>

- Template-literal text:
  <p>{`Hello ${userName}`}</p>

- Function-produced text:
  <p>{formatLabel(product)}</p>

- Long multiline static text
- Text containing apostrophes, quotes, emoji, Unicode, RTL text, and line breaks
- Empty text element
- Whitespace-only text element

B. Repetition and identity

- Three explicit sibling cards written as separate JSX.
- Three calls to one shared Card component with different literal props.
- Three calls to a shared component containing the same hardcoded inner button label.
- A `.map()` over static data with stable ID keys.
- A `.map()` using array-index keys.
- A `.map()` whose text comes from item data.
- A `.map()` containing hardcoded text.
- Nested `.map()` calls.
- A reusable component rendered in two unrelated page sections.
- A component rendered conditionally.
- A component rendered through a fragment.
- A component wrapped in React.memo.
- A component created with forwardRef.
- A component rendered through createPortal inside the dialog.

Clearly show whether a visual edit is expected to affect one instance or all source-sharing instances.

MANUAL TEST PROTOCOL

Display these instructions prominently in the app:

1. Activate Replit Visual Editor.
2. Select the target bearing the displayed test ID.
3. Confirm the correct element is highlighted.
4. Confirm whether related instances are also highlighted.
5. Attempt the change described on the card.
6. Verify the preview.
7. Discard once and verify restoration.
8. Repeat and save.
9. Inspect the resulting source file.
10. Verify only the expected source location changed.
11. Exercise the element’s interaction again.
12. Reload the application.
13. Confirm the change persisted.
14. Check the browser console and build output.
15. Record Pass, Fail, Partial, or Agent fallback in DIRECT_EDIT_TEST_MATRIX.md.

IMPLEMENTATION QUALITY

- Organize test data and reusable display chrome cleanly, but do not abstract away the source patterns being tested.
- Keep explicit JSX cases explicit.
- Keep `.map()` cases genuinely mapped.
- Add comments identifying intentionally difficult patterns.
- Use stable keys wherever the test is specifically about stable keys.
- Use index keys only in the explicitly labeled index-key test.
- Prevent accidental form navigation or full-page reloads.
- Make all normal controls keyboard accessible.
- Provide meaningful alt text and ARIA labels.
- Ensure every test card remains visually distinguishable.
- Ensure the application remains usable on mobile.
- Avoid excessive animation that would make element selection difficult outside the animation-specific tests.

FINAL VERIFICATION

Before finishing:

1. Run the TypeScript check.
2. Run the production build.
3. Open the application.
4. Exercise every interactive demo at least once.
5. Check for browser-console errors.
6. Fix all unexpected errors.
7. Confirm DIRECT_EDIT_TEST_MATRIX.md contains every on-screen test ID.
8. Report:
   - Total number of test cases.
   - Total number of HTML tags covered.
   - Any elements intentionally excluded.
   - Any tests expected to require Agent fallback.
   - Any known browser limitations.

Do not remove failing or difficult cases just to make the app look successful. This application exists to expose Visual Editor limitations.
